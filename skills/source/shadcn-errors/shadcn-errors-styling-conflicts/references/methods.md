# Methods : cn(), tailwind-merge config, cva merge order

Reference material for `shadcn-errors-styling-conflicts`. Treat this file as the deterministic spec for class composition in a shadcn project.

---

## 1. The `cn()` helper : canonical implementation

Every shadcn project ships exactly one version of this file. It is generated by the shadcn CLI when you run `init` and lives at `lib/utils.ts` (or `src/lib/utils.ts` for Vite).

```ts
// lib/utils.ts
import { clsx, type ClassValue } from "clsx"
import { twMerge } from "tailwind-merge"

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs))
}
```

What each layer does inside `cn()`:

| Layer | Job | What happens if you skip it |
|---|---|---|
| `clsx` | Resolves the `ClassValue` argument shapes : strings, arrays, objects with boolean values, and falsy entries. Produces a flat space-separated string. | Conditional shapes (`{ active: isActive }`, `cond && "foo"`) silently break ; arrays are not flattened. |
| `twMerge` | Reads the flat string left-to-right and resolves Tailwind class CONFLICTS using its internal class-group map. Last-wins per family. | Duplicates of the same utility family (e.g., `p-4 p-2`) both reach the DOM ; visual outcome depends on CSS source order, not on the developer's intent. |

Both layers MUST run on every className composition. There is no shortcut.

### When you do NOT need `cn()`

- A single static class string with no composition : `<div className="p-4" />`. No merge work needed.
- A className that is itself the output of a single `cva` call AND has no consumer className : `className={buttonVariants({ variant })}`. cva already ran clsx internally. The moment you need to merge a second source, switch to `cn(buttonVariants(...), other)`.

### When you ALWAYS need `cn()`

- The component accepts `className` from a consumer AND has its own internal classes.
- The component picks from cva variants AND wants to allow consumer override.
- The className depends on a conditional (`active`, `disabled`, theme).
- You touch the same Tailwind family from two different code paths.

## 2. tailwind-merge : configuration knobs

The default `twMerge` export knows every utility from a stock Tailwind install. When a project adds custom classes (a design-system prefix, a custom plugin, a new class group), the merge engine MUST be extended; otherwise it treats those classes as non-Tailwind and stops resolving conflicts against them.

### Custom prefix (Tailwind `prefix` option)

```ts
// Tailwind v3 with prefix: "tw-"
import { extendTailwindMerge } from "tailwind-merge"

export const twMerge = extendTailwindMerge({ prefix: "tw-" })
```

Without this, `tw-p-4 tw-p-2` is treated as two unrelated class names and BOTH reach the DOM.

### Custom class group (plugin-added utility)

```ts
// Example : a custom `--shadow-elevation` family with utilities elevation-1..elevation-5
export const twMerge = extendTailwindMerge({
  extend: {
    classGroups: {
      elevation: [{ elevation: ["1", "2", "3", "4", "5"] }],
    },
  },
})
```

Now `elevation-2 elevation-4` resolves to `elevation-4`.

### Conflicting class groups (utility A invalidates utility B)

```ts
// When `text-balance` should invalidate a previous `text-wrap` value
export const twMerge = extendTailwindMerge({
  extend: {
    conflictingClassGroups: {
      "text-wrap": ["text-balance"],
    },
  },
})
```

shadcn ui itself ships only the stock `twMerge` import. Extending it is a project-level concern; document any extension in your project README so other contributors do not re-introduce duplicates.

## 3. Important-modifier tracking

tailwind-merge maintains a SEPARATE conflict namespace for important utilities. The rule is identical to CSS specificity: an important declaration cannot be overridden by a non-important one, regardless of order.

| Input | Output | Why |
|---|---|---|
| `twMerge("p-3! p-4! p-5")` | `p-4! p-5` | `p-4!` overrides `p-3!` (both important, last-wins). `p-5` cannot displace `p-4!` because it is non-important. |
| `twMerge("p-3 p-4!")` | `p-3 p-4!` | Important wins regardless of which came first. |
| `twMerge("p-4! p-3!")` | `p-3!` | Both important, last wins. |

In Tailwind v3 the important syntax is the PREFIX form `!p-4`; in v4 it is the SUFFIX form `p-4!`. tailwind-merge v3+ supports both, but a single project should pick one syntax and stick to it. Mixing prefix and suffix forms in the same file is the most common cause of "my !important is not winning."

## 4. cva : merge order from first base class to consumer override

cva produces a function that, when called with `{ variant, size, class, className }`, returns a single class string. The order in which classes are concatenated inside that string is FIXED and documented at https://cva.style/docs:

```
1. base                  (the first cva argument)
2. variants              (the selected variant value(s))
3. compoundVariants      (matched compound rules, in declaration order)
4. defaultVariants       (only for props that are undefined at call time)
5. class | className     (consumer override, last in the string)
```

cva runs `clsx` internally over this list so the output is a flat space-separated string. cva does NOT run `twMerge`. To resolve conflicts (which is the whole point of allowing a consumer className), the call site MUST wrap with `cn()`:

```tsx
className={cn(buttonVariants({ variant, size }), className)}
```

### Step-by-step example

```ts
const button = cva(
  "rounded-md text-sm font-medium",                  // [1] base
  {
    variants: {
      tone: {
        brand: "bg-primary text-primary-foreground", // [2] variant value
        ghost: "bg-transparent text-foreground",
      },
      size: { sm: "h-8 px-3", md: "h-9 px-4" },
    },
    compoundVariants: [
      { tone: "brand", size: "sm", class: "shadow-sm" }, // [3]
    ],
    defaultVariants: { tone: "brand", size: "md" },      // [4]
  },
)

// Call site
const out = cn(button({ tone: "brand", size: "sm" }), "px-8")
// [1] rounded-md text-sm font-medium
// [2] bg-primary text-primary-foreground   h-8 px-3
// [3] shadow-sm
// [5] px-8                                  ← consumer
//
// After twMerge : "rounded-md text-sm font-medium bg-primary text-primary-foreground h-8 shadow-sm px-8"
//                                                                                       ↑ px-3 dropped
```

The consumer `px-8` is the last `p*` family entry, so twMerge drops the variant's `px-3`. That is exactly the design.

### Common cva traps

- **`defaultVariants` does NOT fire on explicit empty string.** Passing `variant=""` skips the default entirely. Treat unset values as `undefined`.
- **`compoundVariants` requires ALL listed props to match.** A partial match contributes nothing.
- **`compoundVariants` order matters when two compound rules target the same utility family.** Declaration order = clsx order = twMerge last-wins.
- **`class` and `className` are interchangeable in cva.** Pick one project-wide.

## 5. Diagnostic checklist : "className override does not work"

Run through these in order. Stop at the first match.

1. Open the rendered DOM via DevTools. Count duplicates of the conflicting utility family.
   - 2+ duplicates : cn() was bypassed. Find the call site and wrap it.
   - 1 unique class but wrong value : cn() ran, but merge order is wrong. Continue.
2. Find the cn() call site for this component. Is the consumer `className` the LAST argument?
   - No : reorder.
   - Yes : continue.
3. Does one of the colliding classes use the important modifier?
   - Yes : important is tracked separately. Match the namespace.
   - No : continue.
4. Is one class an arbitrary PROPERTY (`[padding:1rem]`) and the other a utility (`p-4`)?
   - Yes : convert the arbitrary property to an arbitrary VALUE (`p-[1rem]`).
   - No : continue.
5. Is the project Tailwind v4 but the className uses v3 semantics (e.g., `ring-2` expecting 3px, `!bg-red-500` prefix-style)?
   - Yes : update to v4 semantics. See `shadcn-errors-tailwind-v3-v4-migration`.
   - No : the bug is upstream of class merging. Check whether the component forwards className at all.
