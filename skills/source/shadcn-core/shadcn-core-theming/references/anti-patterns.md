# shadcn ui Theming : Anti-Patterns

Six canonical failure modes, each verified from official docs, GitHub issues, or empirical reproduction. Each entry : the symptom, the broken code, the WHY (root cause), and the fix. NEVER ship code matching any of the broken examples.

---

## AP-001 : HSL comma-separated values in v3

### Symptom

Page renders with no colors. Inspector shows `background-color: hsl(0, 0%, 100%)` or `background-color: hsl(NaN)` on `<body>`. The `bg-background` utility appears in the stylesheet but produces no visible color, or the literal string is passed through CSS unchanged.

### Broken code (Tailwind v3)

```css
/* Tailwind v3 : WRONG */
:root {
  --background: 0, 0% 100%;       /* commas inside the variable */
  --foreground: hsl(0, 0%, 3.9%); /* full hsl() wrapper inside the variable */
}
```

```js
/* tailwind.config.js : paired with the wrong CSS */
colors: {
  background: "hsl(var(--background))",
}
```

### WHY (root cause)

The `tailwind.config.js` mapping `"hsl(var(--background))"` substitutes the variable value verbatim. With commas, the result becomes `hsl(0, 0%, 100%)` which is the legacy CSS Colors 3 syntax that modern browsers still accept ; mixing this with Tailwind v3's expected space-separated syntax inside `hsl(...)` produces unpredictable results across browsers (legacy vs modern parser). With the inner `hsl()` wrapper, the result becomes `hsl(hsl(0, 0%, 3.9%))` which IS invalid and silently drops the declaration.

### Fix

```css
/* Tailwind v3 : CORRECT */
:root {
  --background: 0 0% 100%;        /* space-separated triple, no commas, no wrapper */
  --foreground: 0 0% 3.9%;
}
```

Verified at https://ui.shadcn.com/docs/theming (legacy v3 documentation) and reproduced in the shadcn-ui/ui repository.

## AP-002 : Missing hsl() wrapper at the v3 mapping site

### Symptom

Utilities like `bg-background` produce no style. Inspector shows the CSS rule generated by Tailwind but the value is `background-color: 0 0% 100%;` which is invalid and the browser drops the declaration silently. The page renders with browser-default white.

### Broken code (Tailwind v3)

```js
/* tailwind.config.js : WRONG */
module.exports = {
  theme: {
    extend: {
      colors: {
        background: "var(--background)",   /* missing hsl() wrapper */
        foreground: "var(--foreground)",
      },
    },
  },
}
```

With `:root { --background: 0 0% 100%; }` the resulting utility resolves to `background-color: 0 0% 100%;` which is not a valid CSS color value and is dropped.

### WHY (root cause)

In Tailwind v3, CSS variables hold raw color COMPONENTS (the three numbers), not full color values. The `hsl()` function call must wrap them at the consumption site (the `tailwind.config.js` mapping). The decoupling is intentional : the variable can be consumed by `hsl()` OR by `rgb()` separately depending on what the project wants, but the wrapper is mandatory in v3.

### Fix

```js
/* tailwind.config.js : CORRECT */
colors: {
  background: "hsl(var(--background))",
  foreground: "hsl(var(--foreground))",
}
```

Note : Tailwind v4 deliberately reverses this convention (raw color values inside the variable, NO wrapper at the mapping site). Mixing the two conventions in one project is AP-003.

## AP-003 : Mixing v3 and v4 wiring

### Symptom

Some utilities resolve, others do not. The application semi-works in light mode but breaks in dark mode, or works in dev (Vite) but not in production (Next.js build), or vice-versa. Inspector shows a mix of `oklch(...)` and `hsl(...)` declarations.

### Broken code

`tailwind.config.js` (v3 style) :
```js
colors: {
  background: "hsl(var(--background))",
}
```

`globals.css` (v4 style) :
```css
@import "tailwindcss";

:root {
  --background: oklch(1 0 0);
}

@theme inline {
  --color-background: var(--background);
}
```

### WHY (root cause)

Tailwind v4 IGNORES `tailwind.config.js` for the new theming system ; the `@theme inline` directive is the v4 source of truth. Tailwind v3 has no `@theme inline` parser ; it ignores that directive and looks at `tailwind.config.js`. With v4 installed but a v3-style config left in place, the project ends up with two competing color mappings : `bg-background` may resolve to the `@theme inline` mapping (`var(--background)` → `oklch(1 0 0)`) OR to the legacy mapping (`hsl(var(--background))` → `hsl(oklch(1 0 0))` which is invalid and silently dropped), depending on Tailwind's class-generation order.

### Fix

ALWAYS pick ONE generation and remove the other's wiring entirely.

For Tailwind v4 :
- Delete `tailwind.config.js` (or remove its `theme.extend.colors` block)
- Use `@theme inline` exclusively in `globals.css`
- Store full `oklch(...)` values in variables

For Tailwind v3.4 :
- Remove the `@theme inline` block from `globals.css`
- Use `tailwind.config.js` `theme.extend.colors` exclusively
- Store space-separated HSL components in variables, wrap with `hsl()` at the mapping site

Verified at https://ui.shadcn.com/docs/tailwind-v4.

## AP-004 : Storing HSL components in a v4 project (or oklch in v3)

### Symptom

`bg-background` produces no style in a v4 project, OR produces `hsl(oklch(...))` errors in a v3 project. DevTools console shows `Invalid property value` warnings for the affected utilities.

### Broken code (v4 with v3 values)

```css
/* Tailwind v4 : WRONG (HSL legacy format in v4 project) */
:root {
  --background: 0 0% 100%;   /* legacy v3 format */
}

@theme inline {
  --color-background: var(--background);   /* expands to "0 0% 100%" : not a color */
}
```

### Broken code (v3 with v4 values)

```css
/* Tailwind v3 : WRONG (oklch in v3 project) */
:root {
  --background: oklch(1 0 0);
}
```

```js
colors: {
  background: "hsl(var(--background))",   /* expands to "hsl(oklch(1 0 0))" : invalid */
}
```

### WHY (root cause)

In v4, `@theme inline` expects each `--color-*` declaration to resolve to a complete CSS color value. `0 0% 100%` is three numbers, not a color. In v3, the `hsl()` wrapper at the mapping site expects three HSL components inside ; receiving an `oklch()` function call instead produces `hsl(oklch(...))` which is syntactically invalid.

### Fix

ALWAYS match the value format to the wiring :
- v4 : full `oklch(...)` (or `hsl(...)` ALSO works in v4 ; just be consistent and use complete function calls inside the variable)
- v3 : space-separated HSL components without a wrapper

The default values shadcn ships per generation are the canonical reference :
- v4 default style : `oklch(...)` (see `examples.md` Example 2)
- v3 default style : space-separated HSL (see `examples.md` Example 1)

## AP-005 : Missing suppressHydrationWarning + flash-of-unstyled-content

### Symptom

In Next.js, the page flashes light theme for one frame before settling on the user's chosen dark theme (or vice-versa). React DevTools logs : `Warning: Prop className did not match. Server: "..." Client: "... dark"`. Sometimes accompanied by a full hydration mismatch error in strict mode.

### Broken code

```tsx
/* file : app/layout.tsx : WRONG */

import { ThemeProvider } from "@/components/theme-provider"

export default function RootLayout({ children }) {
  return (
    <html lang="en">                                         {/* suppressHydrationWarning missing */}
      <body>
        <ThemeProvider attribute="class" defaultTheme="dark">  {/* enableSystem and disableTransitionOnChange missing */}
          {children}
        </ThemeProvider>
      </body>
    </html>
  )
}
```

### WHY (root cause)

next-themes runs an inline script that mutates `<html>`'s class BEFORE React hydrates the page, so the user sees the correct theme on first paint without a flash. The server-rendered HTML and the client-side hydration tree will therefore differ in `className` : the server emits `<html>` with no class, the client immediately mutates it to `<html class="dark">`. React 18+ detects this discrepancy and logs a hydration mismatch warning. `suppressHydrationWarning` is a special React prop that tells the reconciler to ignore the mismatch on that specific element ONLY. Without `disableTransitionOnChange`, the class swap triggers any CSS transitions on theme-driven properties (e.g., a `transition-colors` rule), producing a visible one-frame flicker.

### Fix

```tsx
/* file : app/layout.tsx : CORRECT */

import { ThemeProvider } from "@/components/theme-provider"

export default function RootLayout({ children }) {
  return (
    <html lang="en" suppressHydrationWarning>                {/* required */}
      <body>
        <ThemeProvider
          attribute="class"                                  {/* required : matches the .dark CSS variant */}
          defaultTheme="system"                              {/* respects OS preference on first paint */}
          enableSystem                                       {/* exposes "system" as a toggle option */}
          disableTransitionOnChange                          {/* suppresses one-frame transition flicker */}
        >
          {children}
        </ThemeProvider>
      </body>
    </html>
  )
}
```

ALL FOUR ThemeProvider props are required. Verified verbatim at https://ui.shadcn.com/docs/dark-mode/next on 2026-05-19. Also tracks shadcn-ui/ui issue #5552 (99 reactions).

## AP-006 : Using --foreground for backgrounds (semantic mismatch)

### Symptom

Components display invisible text (white on white, black on black) in one theme but render correctly in the other. The element uses a foreground variable as a background color or vice-versa.

### Broken code

```tsx
/* WRONG */
<div className="bg-foreground text-background">    {/* swapped : looks fine in light, invisible in dark */}
  Content
</div>

/* WRONG */
<Alert className="bg-destructive-foreground">      {/* destructive-foreground is not in the default catalog */}
  Error
</Alert>

/* WRONG */
<Card className="border-input">                    {/* --input is for form inputs, not card borders */}
  Content
</Card>
```

### WHY (root cause)

The token names encode SEMANTIC roles, not arbitrary color slots :

- `--background` / `--foreground` are paired : background is the larger surface, foreground is text or icons on that surface. Swapping them inverts the contrast intent and produces low-contrast text in one of the two modes.
- `--destructive-foreground` is NOT in the default shadcn token catalog (verified 2026-05-19). Using it produces an unresolved utility that silently drops.
- `--input` is specifically for form input borders ; it has its own dark-mode override calibrated for input visibility against `--background`. Borrowing it for a card produces inconsistent border tone in dark mode (where `--input` uses `oklch(1 0 0 / 15%)` semi-transparent white versus `--border` at `oklch(1 0 0 / 10%)`).

### Fix

ALWAYS pair `bg-X` with `text-X-foreground` :

```tsx
/* CORRECT */
<div className="bg-card text-card-foreground">
  Content
</div>

<div className="bg-primary text-primary-foreground">
  Action
</div>

<Card className="border-border">                  {/* generic border uses --border */}
  Content
</Card>

<Input className="border-input">                   {/* input-specific border uses --input */}
</Input>
```

For destructive text, ALWAYS use one of :
- `text-foreground` (against `bg-destructive`, contrast is usually sufficient for dark text on red)
- A hardcoded `text-white` (the default Button destructive variant ships this)
- Adding a `--destructive-foreground` variable to your custom theme (theme builder does NOT add it by default)

ALWAYS use `cn()` for conditional class composition when toggling between paired tokens :

```tsx
import { cn } from "@/lib/utils"

<Alert
  className={cn(
    "bg-card text-card-foreground",
    variant === "destructive" && "bg-destructive text-white"
  )}
/>
```

NEVER use string concatenation : it bypasses tailwind-merge's conflict resolver and the foreground class may not win over the base one.
